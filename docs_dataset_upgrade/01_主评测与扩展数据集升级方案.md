# 主评测与扩展数据集升级方案

更新时间：2026-04-11

## 1. 背景与问题判断

当前仓库正式数据规模较小：

- `train`: 183
- `valid`: 28
- `test`: 26

按三类任务拆分后，正式测试集仅包含：

- `single_doc_qa`: 14
- `multi_doc_qa`: 7
- `code_qa`: 5

这会带来四个直接问题：

1. 主实验方差过大，单轮结果容易偶然波动。
2. 多 seed 统计不稳定，`P95 ratio` 和任务级 F1 很难形成可靠结论。
3. `code_qa` 样本过少，难以支撑论文级对比。
4. student 蒸馏与策略学习缺少足够训练样本。

因此，建议将当前 `MiniLongBench` 从“主结论数据集”降级为“smoke/快速回归集”，重新建立分层数据体系。

## 2. 最终推荐方案

本项目推荐采用：

- 主评测集：`LongBench_3tasks`
- `single_doc_qa` 扩展集：`NarrativeQA + Qasper`
- `multi_doc_qa` 扩展集：`HotpotQA + MuSiQue`
- `code_qa` 扩展集：`RepoBench v1.1 (Python + Java)`
- 保留当前 `MiniLongBench`：仅用于 smoke/链路验证

该方案的核心原则是：

1. 主评测集必须继续保持“三任务平衡”结构。
2. 扩展数据必须按任务类型分别补强，不能只扩大单一任务。
3. 评测集与训练增强集分离，避免“调参即评测”。

## 3. 选择结论

### 3.1 主评测集：LongBench

推荐将 `LongBench` 作为新的论文主评测来源，但只保留与当前项目直接相关的三类任务：

- `multi_doc_qa`
  - `HotpotQA`
  - `2WikiMultihopQA`
  - `MuSiQue`
  - `DuReader`
- `single_doc_qa`
  - `MultiFieldQA-en`
  - `MultiFieldQA-zh`
  - `NarrativeQA`
  - `Qasper`
- `code_qa`
  - `LCC`
  - `RepoBench-P`

按 LongBench 官方任务表，可得到约：

- `multi_doc_qa`: `200 + 200 + 200 + 200 = 800`
- `single_doc_qa`: `150 + 200 + 200 + 200 = 750`
- `code_qa`: `500 + 500 = 1000`
- 合计约 `2550` 条主评测样本

这和当前 `test=26` 相比，提升幅度足够大，同时任务结构与现有系统设计高度兼容。

官方来源：

- `https://huggingface.co/datasets/zai-org/LongBench`

### 3.2 single_doc_qa 扩展集

#### NarrativeQA

适合补强长文档单文档问答，样本规模大，能明显改善 `single_doc_qa` 稳定性。

官方 split 规模：

- `train`: 65494
- `validation`: 6922
- `test`: 21114

官方来源：

- `https://www.tensorflow.org/datasets/catalog/unified_qa`

#### Qasper

适合补强学术论文类长文档 QA，与当前项目的“证据抽取 + 回答”范式契合。

官方数据说明：

- `5049 questions`
- `1585 papers`

官方来源：

- `https://huggingface.co/datasets/allenai/qasper`

### 3.3 multi_doc_qa 扩展集

#### HotpotQA

适合补强多文档检索、证据融合和多跳推理。

官方数据说明：

- `113k Wikipedia-based question-answer pairs`
- Hugging Face 数据卡显示 `203109 rows`

官方来源：

- `https://huggingface.co/datasets/hotpotqa/hotpot_qa`

#### MuSiQue

适合作为更高难度的多跳扩展集，用于验证真正的组合推理能力。

官方数据说明：

- 论文说明：`25K 2-4 hop questions`
- Hugging Face 数据页显示：`22355 rows`

官方来源：

- `https://huggingface.co/papers/2108.00573`
- `https://huggingface.co/datasets/dgslibisey/MuSiQue`

### 3.4 code_qa 扩展集

#### RepoBench v1.1

最适合当前仓库的代码任务升级，因为现有 `code_qa` 就已经与 `RepoBench-P` 类任务接近。

官方数据规模：

- Python: `23561 rows`
- Java: `26123 rows`

官方来源：

- `https://huggingface.co/datasets/tianyang/repobench_python_v1.1`
- `https://huggingface.co/datasets/tianyang/repobench_java_v1.1`

## 4. 不作为当前主方案的数据集

### QuALITY

`QuALITY` 是很强的长文阅读理解数据集，但它更偏向长文多选阅读理解，而当前项目是开放式问答 + 检索协议框架，不宜作为第一轮主替换对象。

因此建议：

- 暂不纳入主评测集
- 可在后续作为“高难补充 benchmark”单独加入

### 只使用单一大数据集

不建议只改成 `HotpotQA`、`NarrativeQA` 或 `RepoBench` 其中一个，因为这样会破坏当前项目的三任务平衡结构，使论文从“统一端侧长文档系统”退化成“单任务实验”。

## 5. 新的数据分层设计

建议把项目数据层改为三层：

### 5.1 smoke 层

继续保留现有 `MiniLongBench tiny`，仅用于：

- 流程联调
- schema 校验
- 结果文件结构验证
- CI/回归快速检查

### 5.2 main_eval 层

使用 `LongBench_3tasks` 作为论文主评测集：

- 不混入 summarization
- 不混入 synthetic
- 不混入 few-shot 分类
- 只保留与当前研究目标一致的三类任务

### 5.3 train_ext 层

使用任务专项扩展集作为训练增强与泛化验证数据：

- `single_doc_qa`: `NarrativeQA + Qasper`
- `multi_doc_qa`: `HotpotQA + MuSiQue`
- `code_qa`: `RepoBench Python + RepoBench Java`

## 7. 与当前项目结构的映射关系

### 7.1 对主实验的影响

主实验定义不变，仍然是：

- `baseline_rag` vs `edge_agent`
- `formal + sample`
- 三任务平衡

改变的只是：

- 主评测数据从 `MiniLongBench test26` 升级为 `LongBench_3tasks`

### 7.2 对 student 路线的影响

student 路线将直接受益于更大的训练数据：

- 蒸馏控制器可获得更稳定的 `<search>/<final>` 样本
- 任务分布更均衡
- `code_qa` 与 `multi_doc_qa` 不再过于稀疏

### 7.3 对论文叙事的影响

采用该方案后，论文数据部分可以从“小样本可行性验证”升级为：

1. 小规模 smoke 集负责工程可执行性验证。
2. LongBench 三任务子集负责主结论。
3. 任务专项扩展集负责训练增强与泛化验证。

这会比当前单一 `MiniLongBench` 方案更像一套完整论文实验设计。

## 8. 分阶段实施建议

### 阶段 A：最小替换

先做最小风险升级：

1. 接入 `LongBench`
2. 仅抽取三类相关任务
3. 生成 `LongBench_3tasks` 主评测 JSONL
4. 保持现有评测脚本不变

目标：

- 先把主评测规模从 `26` 提升到约 `2550`
- 不立即改 student 训练逻辑

### 阶段 B：扩展训练池

在主评测稳定后，再加入专项扩展集：

1. `single_doc`: `NarrativeQA + Qasper`
2. `multi_doc`: `HotpotQA + MuSiQue`
3. `code_qa`: `RepoBench Python + Java`

目标：

- 扩大 student 蒸馏与训练数据
- 提升任务专项泛化能力

### 阶段 C：高难补充集

最后才考虑加入非同构 benchmark，例如：

- `QuALITY`
- 其他 long-context challenge 集

目标：

- 作为补充实验，而非主结果数据

## 9. 最终决策

本项目推荐最终采用：

1. `MiniLongBench tiny` 作为 `smoke`
2. `LongBench_3tasks` 作为 `main_eval`
3. `NarrativeQA + Qasper + HotpotQA + MuSiQue + RepoBench v1.1` 作为 `train_ext`

一句话概括：

`LongBench 做主评测，任务专项大数据集做训练增强，MiniLongBench 退回 smoke。`

## 10. 后续执行优先级

后续代码改造建议按以下顺序推进：

1. 新增 `prepare_longbench_3tasks.py`
2. 新增统一 `dataset_registry.json`
3. 保持 `run_agent.py / run_baseline_rag.py / evaluate.py` 输入接口不变
4. 再扩展 `prepare_hotpotqa.py / prepare_qasper.py / prepare_repobench.py`

当前不建议一开始就同时接入所有数据集，以免数据规范、schema 和任务映射同时失控。
